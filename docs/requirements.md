# 需求与边界

记录日期：2026-11-05。

状态：讨论稿。本文区分用户明确提出的需求和待确认的设计建议；不是已批准的实现设计。

## 使用背景

用户拥有多个项目，大多数在本地部署，另有一个项目部署在服务器上。Docker 容器较多，目前难以明确容器与项目的关系、公共服务的使用范围及项目启动方式。

## 用户明确提出的需求

1. 汇总全部项目，并支持项目分组。
2. 列出每个项目使用的容器。
3. 列出公共容器及使用它们的项目。
4. 发生问题后，能找到对应容器进行维护与修改。
5. 点击一次按钮即可启动完整项目，覆盖容器和本机进程。
6. 启动按钮执行项目保存的脚本，脚本可以编辑。
7. 优先改善本地项目管理，服务器管理的优先级较低。
8. 管理工具交付为桌面程序，同时支持配置一键导出、迁移和导入识别。
9. 本工具使用 Git 进行版本管理，公开托管到 GitHub 的 `JeropsWang` 账号。
10. 规范导入导出兼容性，检查缺失文件及依赖，避免导入后配置损坏或无法使用。
11. 采用独立桌面程序路线，首版只做 Windows。
12. 检测目标电脑的环境配置，明确各项目版本所需的运行环境条件。
13. 同时提供自动准备项目独立环境、仅检测并提供修复步骤两种模式，由用户选择。
14. 用户须先初始化环境存放位置，选择具体磁盘与文件夹，再准备环境。
15. 关闭管理器窗口后，已启动的项目继续在后台运行。
16. 明确退出管理器时，安全停止全部已启动项目，完成后退出管理器。
17. 默认采用专业中性风格，允许个性化封面，并加入动态排版、视差效果和颗粒质感。
18. 源码需要有效注释、统一格式化和正常换行；页面、CSS、路由、服务和业务逻辑分层组织。
19. 核心语言与桌面框架选用 Go + Wails；前端技术由用户授权助手结合实际需要选择。
20. 项目技术类别包括 Vue、React、Next.js、Go、Python、Java、PostgreSQL、MySQL 等；以指定项目核查确定兼容方案。
21. typing-tracker 与 WeChatBot 以用户 GitHub 仓库为准，PersonWeb 以本地为准。默认分支、正式发布与本地运行实例应分别识别。
22. 首版优先完整接入上述三个项目；Java、MySQL 等先提供识别、环境检测和修复报告，后续按真实项目样本扩展自动准备。

工作空间和环境处理的详细讨论记录见 [环境文档](environments.md)。已选择 Go + Wails；前端由助手选用 React + TypeScript + Vite，详情见 [技术选型](technology-selection.md)。已确认的视觉方向见 [视觉文档](visual-direction.md)，具体布局、配色和效果尚待原型确认；软件工程约定见 [分层文档](engineering-conventions.md) 和 [AGENTS.md](../AGENTS.md)。

指定项目核查形成的 [兼容设计草案](superpowers/specs/2026-11-05-compatibility-design.md) 区分静态声明、依赖元数据、环境观察和实际验证。本机详细路径与容器清单仅保存在被 Git 忽略的审查报告。

## 建议的资源关系

以下为设计建议，尚待确认。

- 项目：保存分组、代码位置、运行说明和启动入口。
- 运行单元：容器服务、本机长期运行进程、初始化任务。
- 公共服务：可供多个项目依赖的运行单元。
- 使用关系：记录项目依赖哪些服务；区分专用归属与公共依赖。
- 本机配置：保存实际路径、解释器、端口和环境变量来源。

项目与公共服务是多对多关系。不能仅根据容器名称推断真实业务用途；扫描结果需结合 Compose 标签和人工关联确认。关联应使用稳定的配置标识，避免将会随重建变化的容器 ID 当作永久身份。

## 建议的一键启动行为

1. 检查项目目录、运行环境、Docker 连接、端口和必要配置。
2. 解析依赖关系；阻止循环依赖和同一项目的重复启动。
3. 检查并启动所需公共服务，复用已运行实例。
4. 启动专用容器，按项目配置检查服务就绪。
5. 执行初始化任务，随后启动本机后端、前端等进程。
6. 分别展示各步骤、进程和容器的输出与状态。

脚本成功退出、进程仍在运行、应用已能访问，应显示为不同状态。初始化任务和数据库迁移的重跑条件需单独配置，不建议每次启动都盲目执行。

## 建议的停止和故障处理行为

- 停止项目时，按依赖顺序停止本工具管理的项目进程及专用服务。
- 单独停止一个项目时，公共服务默认保持运行；全局退出时按归属和使用关系处理公共服务，详见环境文档。
- 已经由用户自行启动的外部进程或公共服务，不能因为一次启动失败而被自动结束。
- 本地命令需明确工作目录、解释器和参数，并跟踪子进程；仅关闭终端窗口不足以保证服务结束。
- 维护入口可包括容器日志、终端、重启、端口、挂载及配置位置；持久修改应落到 Compose、挂载配置或镜像构建来源。

## 桌面交付与导出

已确认需要桌面程序、配置一键导出与迁移、导入识别，以及兼容性和缺失文件检查。以下为建议的拆分，额外文件的携带范围尚未确定。

| 产物 | 作用 | 待确认范围 |
| --- | --- | --- |
| 桌面安装包 | 安装本管理工具，首版仅 Windows | 支持的 Windows 版本、架构，安装与便携形式 |
| 项目导出包 | 迁移项目配置 | 脚本及引用配置的收集规则；是否额外包含源码、镜像和数据 |
| 项目导入 | 在目标电脑恢复项目登记与运行配置 | 路径重绑定、公共服务匹配、运行环境检查 |

建议导出包带格式版本与文件清单，采用相对路径或路径变量。Node/Python/Java 等本机运行环境必须说明版本与安装要求；仅保存启动脚本不能保证换机器即可运行。具体兼容检查建议见 [配置迁移文档](portability.md)。

建议公共服务通过稳定标识和依赖说明引用，导入时匹配已有服务或引导配置，避免重复创建同一公共服务。跨电脑的服务版本和端口冲突需要明确处理。

建议默认导出配置、脚本与环境变量模板；源码及构建产物按需选择。镜像与业务数据作为显式选项。数据库数据需通过备份流程导出，不能把运行中的数据目录直接当成一致性备份。

导入的脚本应先可查看与编辑，导入本身不执行脚本。此为本地命令执行工具的行为建议。

## Git 与公开仓库

本工具的文档与后续代码在本仓库管理。被管理项目各自的 Git 仓库保持独立；当前用户没有要求自动将所有业务项目上传到公开 GitHub。

本仓库不收录实际工作区登记、机器路径、真实 `.env`、凭据、运行日志、项目导出文件、镜像及业务数据。后续若提供示例，仅使用虚构项目与占位配置。

## 仍需讨论

- 已选技术栈的具体依赖版本、接口契约和数据模型。
- 本地 Docker 运行在 Docker Desktop、WSL、其他环境还是多种环境。
- 首版的具体配置格式、模块接口及验收标准；尚缺样本的 Java、MySQL 等工程的具体声明与运行要求。
- 一键导出的默认内容、离线运行要求、Windows 版本与架构范围。
- 异常退出和系统重启后的恢复检查策略；关闭窗口继续运行、明确退出时安全停止项目已确认。
- 首版必要的容器维护操作。
- 是否需要记录公共服务内部数据库、Redis 命名空间等更细粒度的依赖。

## 建议的试点验收场景

以下为后续讨论实现范围时可使用的场景，不代表已批准的实施计划。

选择两个本地项目，共用一个公共服务，且至少一个项目包含本机前后端进程：能够双向查看项目与容器关系，一键启动完整项目并定位失败步骤，停止一个项目时不影响另一个项目的公共依赖，导出后可以在重新映射路径的环境中导入并检查所需配置。
