# 开源参考与候选路线

状态：比较草案，尚未选定路线或技术栈。

## 参考项目

| 项目 | 官方资料中的能力 | 对本需求的评估 |
| --- | --- | --- |
| [Tilt](https://github.com/tilt-dev/tilt) | 本地命令、常驻进程、资源依赖及 Docker Compose 接入 | 值得研究混合启动编排；项目台账、公共容器归属和项目导出仍需评估或补充 |
| [Dockge](https://github.com/louislam/dockge) | 围绕 Compose 管理服务栈、编辑配置和执行启停更新 | 适合参考容器维护与配置保存；宿主机进程、桌面交付和项目导出需要额外设计 |
| [Komodo](https://github.com/moghtech/komodo) | 服务器、Compose Stack、标签、构建及自动化流程 | 功能广，未来服务器场景可参考；当前本地优先的需求要衡量部署及二次开发成本 |
| [Portainer CE](https://github.com/portainer/portainer) | 通用容器管理、Compose Stack 部署 | 适合参考容器维护入口；完整本地项目启动与迁移不是本次已核实能力的重点 |

注意 Tilt 的资源依赖文档说明：Compose 资源的默认就绪条件是容器已启动，并不观察 Compose 健康检查；资源依赖主要影响一次 `tilt up` 后的首次启动。若采用它，需要针对应用就绪、重试和公共服务生命周期做适配验证。

上表的适用性判断是针对本需求的分析，不代表已经运行验证这些项目，也不代表它们完全不具备其他能力。

## 路线 A：以 Tilt 为基础扩展

复用其本地进程与容器编排，再补充多项目目录、公共服务关系、脚本编辑、导出导入及桌面交付。

优点：已经具备本地命令、常驻服务与依赖顺序模型。

代价：需要评估现有资源模型能否承载跨项目公共服务，以及桌面包装与二次开发的维护成本；不能只凭功能列表就认定能直接复用。

## 路线 B：以 Dockge 为基础扩展

以 Compose 管理为基础，增加项目台账和宿主机执行能力，再设计桌面交付与导出。

优点：与容器维护需求接近，配置文件直接保存的方式便于理解和维护。

代价：容器中的管理服务不能自然地管理 Windows 宿主机进程，需要本机代理或改变应用运行结构，不能仅增加几个页面。

## 路线 C：独立桌面程序，复用 Docker 与进程执行能力

围绕用户的项目模型构建桌面程序，调用本机 Docker/Compose 和进程执行接口；从 Tilt、Dockge 参考交互与资源管理思路，按需复用兼容组件。

优点：项目归属、公共依赖、本机脚本和导出格式可以在同一个模型里设计，直接面向本地工作方式。

代价：需要自行实现进程跟踪、日志、执行状态、依赖控制和打包；工作量不能按一个简单容器面板估算。

## 当前建议

倾向路线 C，理由是本需求同时要求本机进程、容器关系、桌面交付与项目导出，改造纯容器管理服务可能涉及较大运行结构调整。路线 A 值得先做兼容性研究，确认能否减少启动编排部分的工作。

这是助手的建议，用户尚未选择。首发系统、Electron/Tauri 等框架以及具体实现技术均未定。

公开仓库不等于已经选择开源许可证。当前未复制参考项目代码；若后续 fork 或复用代码，需要保留来源并按所用代码的许可证处理。
