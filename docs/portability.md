# 配置迁移与兼容规则建议

记录日期：2026-11-05。

用户已确认：配置应可直接迁移，支持导入识别，并规范兼容性，避免导入缺文件或不可用。

本文保留早期规则讨论。具体字段和实现边界以工程设计与配置契约为准。首轮验收 Windows 11 x64，格式 1.0。管理核心已有固定版本 ZIP 导出、只读预览和事务导入。预览保留 30 分钟，正式登记前重新读取并核对包内容。已有同 ID 的项目会保留，已有同 ID 的容器资源须先处理绑定冲突。[工程设计](superpowers/specs/2026-11-05-engineering-design.md) · [配置契约](contracts/README.md)

导出在目标目录生成临时 ZIP，重新校验原始字节后用硬链接发布。目标卷需要支持硬链接，已有目标文件会保留。Compose 随包引用当前限于明确声明的相对文件。构建上下文、宿主机挂载、真实环境文件和无法核对的动态路径需要作为外部配置处理。脚本预览会提示动态文件依赖尚未经静态验证。

## 迁移内容的边界

建议首版导出项目声明、分组、服务关联、脚本、Compose 及其必需引用配置、环境变量模板和运行要求。

每项依赖必须明确属于以下一种：

1. 随包携带：包内有文件，清单记录相对路径、大小和 SHA-256。
2. 目标电脑提供：源码目录、运行环境、公共服务、密钥等，清单记录检查规则及重新绑定要求。
3. 导入或启动时生成：注明生成步骤、所需输入和执行条件，不把它当成遗漏文件。

公共服务记录稳定标识和兼容要求，不把源电脑的容器 ID 作为迁移依据。首版聚焦配置，源码、镜像、制品、模型、运行时和业务数据不随包携带，完整外部要求必须列明；详见已确认的兼容设计。

## 建议的包结构

使用 ZIP 承载一个项目的配置，包含一个固定入口清单，以及配置和脚本文件。入口清单建议表达：

| 信息 | 用途 |
| --- | --- |
| 包格式标识、格式版本、生成工具版本 | 识别包类型，判断能否读取或升级 |
| 项目标识、运行单元及依赖关系 | 恢复归属关系并检查重复或循环依赖 |
| 文件清单、大小、SHA-256 | 检查缺文件、损坏和内容变化 |
| 支持的系统、架构、Shell、执行目录 | 判断脚本能否在目标环境运行 |
| Docker/Compose、镜像及本机运行环境要求 | 检查运行能力与版本要求 |
| 外部路径变量、环境变量名、公共服务引用 | 指出需要重新绑定或补充的内容 |
| 包含范围、生成文件、联网要求 | 区分完整配置包与离线运行包 |

配置格式版本和应用版本分别管理。包中不保存真实密码；需要的变量在导入报告中列出，补齐后才允许相关服务启动。

文件校验用于确认清单与包内容一致，不代表脚本来源可信。导入和格式升级都不自动执行其中的脚本。

## 文件收集与缺失检查

- 导出前检查所有已声明的必需文件；缺少随包文件时阻止生成成功结果。
- 对 Compose 关联的 `env_file`、`configs`、`secrets`、相对绑定挂载、`include`、`extends` 和构建上下文，分类为随包文件、外部依赖或不支持的配置。
- 敏感文件按外部依赖处理并明确报告，不以省略后假装完整的方式导出。
- 绝对路径转换为需要绑定的路径变量，不能原样当成目标机器上有效的路径。
- 任意用户脚本可能在执行时动态访问文件，无法仅靠静态扫描保证穷尽依赖。需要显式声明附加文件和外部要求，并在导出报告中标明无法验证的部分。
- 镜像标签、平台及必要版本应有记录；若未携带镜像，明确要求目标机已有镜像或能够联网拉取。

## 建议的导入流程

1. 在临时目录检查包类型、清单、文件数量与体积限制，拒绝路径越界和可逃出目标目录的链接。
2. 验证格式版本、必需字段及每个声明文件的大小和校验值；必需文件损坏时拒绝导入。
3. 检查项目标识冲突和依赖图，不静默覆盖已登记项目或公共服务。
4. 将旧版本配置迁移到当前内部格式；保留原包，不能识别的新版本给出明确原因。
5. 引导绑定源码目录、外部文件、公共服务和环境配置。
6. 检查平台、Shell、运行环境、Docker/Compose 能力、镜像架构、端口及挂载路径。
7. 先展示检查报告，再保存登记结果；导入本身不启动项目。

建议状态区分为“配置有效”“待补充环境”“可启动”。配置有效但目标机没有源码或 Docker 尚未运行时，可以保存为待补充状态；不能显示为可启动。

用户已确认环境准备前必须先初始化存放目录，并可选择自动准备独立环境或仅检测并提供修复步骤。导入识别、环境准备和启动是分别触发的操作；具体讨论记录见 [环境文档](environments.md)。

导入失败应清理本次临时文件并保留已有项目状态。即使用户后来选择启动，也不得自动修改公共数据库、删除现有数据或覆盖其他项目配置。

## 兼容策略建议

| 情况 | 建议行为 |
| --- | --- |
| 已支持的格式版本，环境满足要求 | 导入并标记可启动 |
| 已知旧格式且有迁移规则 | 迁移副本，重新校验，保留原包 |
| 未知新格式或无迁移路径 | 拒绝导入并说明所需工具版本 |
| 包内必需文件缺失或校验失败 | 拒绝导入，列出具体文件 |
| 缺外部文件、运行环境、环境变量或服务 | 报告补齐方式，标记待补充，阻止相关启动 |
| 同名项目或公共服务 | 按稳定标识与配置比较处理，不凭名称合并 |
| 系统、架构或 Shell 不兼容 | 显示具体冲突，要求适配；不声称通用兼容 |
| 检查受网络或 Docker 未运行影响 | 标记未验证，并在启动前重新检查 |

“项目配置可迁移”不意味着所有本机脚本跨操作系统可运行。首版已限定 Windows，仍需检查 Windows 版本、CPU 架构、Shell 和 Docker 容器模式等差异。

## 建议验收场景

- 在同平台另一台电脑导入，重新绑定源码路径并补齐环境后能够启动。
- 删除包中一个必需文件后，导入准确指出缺失文件且不覆盖已有配置。
- 修改包中脚本但保留旧校验值，导入拒绝该损坏包。
- 目标机缺少运行环境、外部配置或必要环境变量，报告可执行的补齐项。
- 不兼容格式、Shell 或镜像架构均有明确提示。
- 导入两个依赖同一公共服务的项目，不静默创建或合并冲突服务。
- 导入过程不执行脚本；任意失败不会损坏原有项目登记。
