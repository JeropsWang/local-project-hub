# 软件工程约定与分层建议

日期：2026-11-05。状态：用户已确认可维护性和职责分层要求；以下具体目录和边界是落实建议，完整技术架构尚待最终确认。

## 用户明确要求

- 编写有效注释。
- 统一格式化，不能把代码挤在一行。
- 页面、CSS、服务层、路由层、业务逻辑分别存放。
- 做好架构分层，不能把全部实现堆在同一文件夹。

这些要求同时约束文件组织和依赖方向。仅拆文件、仍由页面直接操作 Docker 或承担完整业务流程，不满足分层意图。

## 目录建议

已选择 Go + Wails；前端由用户授权助手选用 React + TypeScript + Vite，样式采用 CSS Modules。以下为目录建议，尚未实际创建应用源码或安装依赖。

```text
main.go               仅负责启动与退出码处理
assets.go             仅负责嵌入构建后的前端资源
frontend/
  src/
    pages/            页面入口，按项目、容器、环境等功能分组
    components/       可复用展示和交互组件
    css/              基础样式、主题、页面样式、动效与纹理样式
    router/           路由声明与导航
    services/         Go 桥接通信、事件订阅和接口适配
    business/         界面用例、交互流程和展示模型
    stores/           界面状态与运行状态的展示快照
    types/            类型声明与接口契约
    animations/       动效适配、作用域与清理
    assets/           图标、封面和纹理资源
internal/
  bootstrap/          依赖组装、Wails 启动和应用生命周期
  desktop/
    services/         暴露给界面的服务入口和参数映射
    events/           核心事件向界面的映射
  domain/             项目、服务、版本要求等模型及规则
  application/        检测、准备、启停、导入导出等用例
  ports/              核心访问外部能力的接口
  adapters/
    docker/           Docker 连接与 Compose 调用
    process/          Windows 进程、脚本和进程树管理
    environment/      环境探测与支持的准备步骤
    filesystem/       路径、文件收集和归档读写
    persistence/      配置及本机记录持久化
tests/                跨模块验证及虚构测试样例
docs/                 需求、设计与开发约定
```

顶层按职责分层，层内再按业务功能拆分。文件在承担多项无关职责时拆分，不能把全部用例放进一个页面、一个通用 service 或一个巨型业务文件。

## 职责与依赖方向

前端页面触发界面用例，由服务接口提交核心操作；服务层只做通信与数据映射。前端业务模块可处理表单、筛选、交互和展示模型，但实际运行环境、资源归属与启停状态以核心为准。

Wails 桌面服务层只处理请求校验、上下文和用例调用。核心用例组织领域规则，通过 ports 调用外部能力；具体适配器实现 ports，由 bootstrap 在应用启动时组装。main.go 保持为薄入口，不承载业务流程。

`domain` 和 `application` 不依赖 Wails、Docker 客户端、数据库驱动或 Windows API；`adapters` 实现 `ports` 定义的接口，业务用例不能反向导入具体适配器。核心需可在不打开桌面界面的情况下验证。

路由中不实现部署或环境准备。状态容器不代替业务层。CSS 与业务分开，视差输入只更新动态参数，位移、遮罩和纹理规则放在对应 CSS 模块。

## 注释规范

模块说明自己的职责和不负责的部分；业务接口说明输入、前提、输出与错误。异步长任务说明取消、超时和重试的行为，共享资源操作说明归属及影响范围。

Go 的导出业务接口、类型和关键用例使用文档注释；TypeScript 的公共业务和服务接口使用文档注释；CSS 按主题、组件或效果说明必要的设计意图。简单明显的代码不逐行复述，复杂分支不能没有解释。

## 格式化与验证

Go 使用统一格式化、go vet 与适用的测试；前端采用 Prettier、ESLint 和 TypeScript 类型检查，在仓库中统一配置。Vite 构建不替代 TypeScript 类型检查。源码保留多行结构，构建压缩输出不作为人工维护源码。

重点验证兼容条件、未知环境、导入缺失与损坏、路径绑定、循环依赖、公共服务和安全退出。界面验证覆盖主题、列表与封面展示、动态布局、减少动态效果设置和不同窗口尺寸。
